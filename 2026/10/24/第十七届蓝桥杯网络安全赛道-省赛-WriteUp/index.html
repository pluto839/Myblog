派生表构造

A（24B）先生成一个小表，与 B、C 混合成一个约 256 字节的查找区，再与 D 混合构造出索引扰动 / 局部置换 / 按位旋转 / 查表替换 / 状态反馈所需的状态表。

看不懂像什么？因为它本来就不像标准算法，更像一个小型自定义流变换器。这种设计的目的就是让你无法用”识别算法 → 找现成解法”的路子。

关键陷阱：第一条分支是 decoy

校验流程分两段：

  1. 先做一条”主分支”变换后比较
  2. 主分支不通过，再进入”回退分支”做另一套变换并比较

第一条分支是干扰项，真正的 flag 在 fallback 分支里。 如果只盯着第一条比较分支逆推，会一直得到”看似有解但通不过”的结果。

复现思路

支持内部文档搜索、记录偏好、自动生成执行计划。audit_token 导出只有在”最新计划包含审批信息”时才允许执行。

那句 hint 是全题的钥匙：planner 和 dispatcher 共享同一份持久状态。

学到的点

这道题让我第一次认真思考 Agent 系统的权限边界。传统 Web 的信任边界是”用户输入 vs 服务端逻辑”，但在 Agent 工作流里多了一条更隐蔽的边界：工具 A 的输出 → 工具 B 的输入，中间那一层缓存。

任何”跨阶段共享状态”都需要回答三个问题：

  1. 这个状态是谁写的？
  2. 下游消费它的时候，有没有校验来源可信度？
  3. 审批 / 授权这类关键字段，应该从哪个可信通道产生，而不是从”缓存里恰好有”来判定？

现实的 prompt injection 很多就长这个形状：网页、文档、邮件里的内容被 RAG 检索进来，然后被 planner 当成指令或授权执行。

省赛小结

12 道题解出 8 道。复盘下来，三种能力最关键：

第一，认特征比硬刚重要。 r 相同 → nonce 复用；s_good / s_fault 成对 → Bellcore；源码里 random.seed(公开参数) → XOR 直接破。这些模式认出来就是 5 分钟，认不出来能耗一整天。

第二，工具的”默认行为”经常是障碍。 curl 默认规范化路径，--path-as-is 才能穿越；SQLite 默认会 checkpoint，-wal 里才有旧数据；HEAD 请求没有 body，数据只在响应头。知道工具在偷偷帮你做什么，才知道怎么关掉它。

第三，逆向先动态跑一遍。 veil_gate 的 decoy 分支如果用静态思路去逆，会一直在错的方向上得到错的结果。先跑、先看哪条路径输出了 ok，能省下大量时间。
